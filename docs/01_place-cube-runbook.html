00전체 흐름

아래 순서대로 하면 된다. 사람이 직접 하는 것은 3번(시연 녹화)과 6번(학습 중 개입)뿐이고 나머지는 명령 한 줄씩이다. 각 단계의 자세한 내용은 아래 번호 절에 있다.

  1. 환경 만들기 씬 XML + 환경 클래스 + 등록. 성공 판정이 “타겟 안에 놓임 + 바닥에 닿음 + 그리퍼 열림”인지 확인 완료.
  2. 설정 파일 만들기 연습용·녹화용·스모크용·본학습용 4개. 녹화 파이프라인과 학습 배선 모두 통과.
  3. 시연 녹화 — 사람이 하는 일 키보드로 30개 이상. 10개씩 나눠서 해도 된다. 30~50분. 성공한 것만 쓴다.
  4. 병합 + 통계 갱신 merge_demos.py --success-only → update_dataset_stats.py. 각 1분.
  5. 스모크 테스트 3,000 스텝만 돌려 배선 확인. 5~10분.
  6. 본 학습 + 개입 learner / actor 두 개를 띄우고, 정책이 못 하는 판에 Space 로 끼어든다. 초반에 개입을 많이 할수록 빨리 배운다(실측: 개입 없이 100판 1% → 개입 40판 52%).
  7. 평가 · 기록 report.py 로 그래프를 남기고, 체크포인트를 재생해 실력이 느는 것을 영상으로 본다.

다른 GPU 서버로 옮길 때

nvidia-gl/ 은 이 서버의 드라이버 버전에 묶인 파일이다. 프로젝트를 통째로 복사해 가면 같이 따라간다.

  • 그 서버 컨테이너에 그래픽 라이브러리가 없으면(이 서버와 같은 경우) — 거기서 05_nvidia_gl.sh --force 를 다시 돌린다. ICD 파일에 프로젝트 절대경로가 박혀 있어서, 경로가 달라도 다시 돌려야 한다.
  • 그 서버가 그래픽 라이브러리를 이미 갖고 있으면(ldconfig -p | grep libEGL_nvidia 가 나오면) — nvidia-gl/ 이 오히려 엉뚱한 버전으로 덮어쓴다. rm -rf nvidia-gl 로 지운다. 점검 스크립트가 이 경우를 알려 준다.
  • GPU 가 없는 곳이면 EGL 이 CPU 로 돈다. 돌기는 하지만 actor 가 실시간(20 fps)을 못 맞춘다.
  • GPU 종류가 다르거나(RTX 5090 등) 대여 서버(RunPod)로 옮기면 — 무엇이 자동으로 맞춰지고 무엇을 손대야 하는지(버퍼 크기), 설치 스크립트가 각각 무엇을 보고 갈라지는지(04 핸드북 §07 스크립트 지도), 첫 서버 검증 절차는 §12. RunPod 에서 칠 명령 순서(pod 만들기 · 설치 · tmux · 학습 · 멈추기 · 다시 켜기)는 05 RunPod 실행 절차.

느렸던 원인은 창이 아니라 MUJOCO_GL=glfw 였다

이 서버의 X(VNC) 는 OpenGL 을 GPU 가 아니라 소프트웨어(llvmpipe)로 잡는다 (glxinfo -B 로 확인: OpenGL renderer string: llvmpipe). MUJOCO_GL=glfw 로 두면 창이 없어도 정책 카메라 렌더링이 그 소프트웨어 경로를 타서 40배 느려진다. MUJOCO_GL=egl 이면 A100 으로 그린다.

구성MuJoCo 창MUJOCO_GL스텝당실효 fps
지금 기본값없음egl22.9 ms43.7
--window있음egl28.2 ms35.5
예전에 쓰던 것없음glfw859 ms1.2

즉 창은 거의 무료다(23 → 28 ms). 띄우고 싶으면 띄워도 된다: bash scripts/teleop.sh --window. 스크립트들이 MUJOCO_GL=egl 을 강제하므로 예전처럼 느려지지 않는다.

VNC 브라우저 탭을 열어 보고만 있는 것은 공짜다 — 그 바탕화면에 아무것도 안 그려지면 인코딩할 것도 없다.

40초로 늘리면 생기는 비용
영향
벽시계 시간 이게 유일하게 큰 비용이다. 실패한 롤아웃이 20초가 아니라 40초를 먹는다. 학습 초반엔 거의 다 실패하므로 시간당 에피소드 수가 절반이 된다. 성공하면 그 즉시 끝나므로, 잘하게 된 뒤로는 차이가 없다
온라인 버퍼 20,000 프레임 = 에피소드 50개 → 25개분. 다양성이 줄어든다. 거슬리면 online_buffer_capacity 를 40,000 으로 올린다(메모리 여유 충분: 384 GB 중 8 GB 사용 중)
할인율(0.995) 문제 없다. 유효 시야가 1/(1-0.995) = 200 스텝 = 10초인데, 이 과제는 스크립트로 75 스텝이면 끝난다. 40초 상한은 “느리게 해도 봐준다”일 뿐 학습을 어렵게 하지 않는다
학습 품질 사실상 없음. 오히려 사람이 여유 있게 시연할 수 있어 시연 품질이 올라간다

스모크 설정도 같이 조정했다: 한 에피소드가 800 스텝이 되었으므로 online_steps 1,000 → 3,000, steps 800 → 2,000. 안 그러면 에피소드가 하나도 끝나지 않아 체크포인트가 생기지 않는다(예전에 겪은 문제).

언제 끼어드나

Space 한 번이면 개입이 켜지고, 그 순간부터 정책 대신 내 키 입력이 로봇을 움직인다. 다시 Space 를 누르면 정책에게 돌려준다. 개입 중에 모은 전이는 온라인 버퍼와 시연 버퍼 양쪽에 들어가서 보통 데이터보다 훨씬 자주 재사용된다. 그래서 개입 한 번의 효과가 크다.

영상으로 보기 — 로봇이 움직이는 화면

학습이 도는 동안 actor 는 쉬지 않고 로봇을 움직인다. 그 화면은 대시보드 맨 위 칸에 영상으로 나온다. 카메라 두 개(정면 · 손목)를 20 fps 로 흘려준다. 대시보드를 띄워 두기만 하면 된다 — 따로 켤 것이 없다.

창도 같이 띄울 수 있다

학습 중에 MuJoCo 창을 보고 싶으면 bash scripts/train.sh actor --window 로 띄운다. MUJOCO_GL=egl 이 강제되므로 스텝당 23 → 28 ms 정도만 늘어난다(01 참조). 대시보드 영상은 창과 무관하게 계속 나간다.

학습 중 화면은 실력이 아니다

"GPU 를 더 쓰면 빨라지나?" — 절반만 맞다

데이터 수집은 안 빨라진다. actor 는 20 fps 실시간에 묶여 있고 물리 연산은 CPU 다. 학습(최적화)은 빨라진다. 실제로 재 보니 병목은 GPU 연산이 아니라 CPU→GPU 데이터 전송이었다.

배치 256 을 뽑는 시간배치당최대 배치/초
storage_device: cpu (예전)41.2 ms24

이미지가 float32 라 전이 하나가 384 KB, 배치 256 이면 96 MB를 매번 옮기고 있었다. 버퍼를 GPU 에 올려 없앴다 — 29.3 GB 를 쓰고 A100 79 GB 중 45 GB 가 남는다. CPU 로 되돌리려면 --policy.storage_device=cpu.

둘은 따로 돈다. learner 는 actor 를 기다리지 않고 버퍼에 있는 것으로 계속 학습한다.

batch 는 스텝 개수가 아니라 "전이 개수" 다

최적화 스텝 하나가 하는 일 (utd_ratio=2, batch_size=256)
최적화 스텝 1회
 ├─ 배치 ①  256개 전이  =  온라인 128 + 시연 128   -> 크리틱 갱신
 └─ 배치 ②  256개 전이  =  온라인 128 + 시연 128   -> 크리틱 + 액터 + 온도 갱신
                                                      + 타깃 네트워크 소프트 갱신
  합계: 512개 전이를 뽑아 본다
batch_size 256한 번 갱신할 때 쓰는 전이(스텝) 개수. 시간 단위가 아니다
utd_ratio 2최적화 스텝 하나당 배치를 몇 개 뽑을지
online_ratio 0.5배치마다 절반은 온라인, 절반은 시연 버퍼에서
5:5 섞기는 "주기"가 아니라 매 배치다

OnlineOfflineMixer.sample() 이 호출될 때마다 n_online = int(256 × 0.5) = 128, n_offline = 256 − 128 = 128 을 각 버퍼에서 따로 뽑아 이어 붙인다(data_mixer.py). 즉 배치 하나하나가 이미 5:5 다. "몇 스텝마다 한 번 섞는다" 같은 것은 없다.

실측 기준: 초당 3.2 최적화 스텝 × 배치 2개 = 초당 약 6.4번 섞는다. 그동안 actor 는 초당 20개 전이를 새로 만든다.

재개하면 설정 파일 수정은 무시된다

재시작 직후 몇 분간은 성적이 무너진다 — 무작위 정책으로 돈다

체크포인트가 잘못된 것이 아니다. 가중치·옵티마이저·학습 스텝은 온전히 복원된다. 문제는 그 가중치가 actor 에게 도착하기까지 시간이 걸린다는 것이다. 그 사이 actor 는 무작위로 초기화된 정책으로 환경을 돌린다.

왜 이렇게 되나 — learner 의 순서 때문이다

third_party/lerobot/src/lerobot/rl/learner.py
342  policy = make_policy(...)                    # 무작위 (pretrained_path=None)
358  push_actor_policy_to_queue(...)              # ← 벌써 actor 에게 보낸다
364  replay_buffer = initialize_replay_buffer(...)          # 온라인 버퍼 로딩
369  offline_replay_buffer = initialize_offline_replay_buffer(...)  # 시연 버퍼 로딩
392  load_training_state(...)                     # ← 진짜 가중치는 여기서

체크포인트의 train_config.json 은 pretrained_path: None 이라 make_policy 가 가중치를 싣지 않는다. 진짜 가중치는 algorithm/model.safetensors 에서 load_training_state 가 따로 복원한다. 그런데 push 가 그보다 먼저다. 버퍼(온라인 40,000 + 시연 40,000, parquet 약 1.3 GB)를 읽는 시간만큼 이 창이 길어진다.

여기에 actor 쪽 사정이 겹친다 — 가중치를 에피소드가 끝날 때만 갈아 끼운다 (actor.py:398-401):

actor.py
if done or truncated:
    logging.info(f"[ACTOR] Global step {interaction_step}: Episode reward: {sum_reward_episode}")
    update_policy_parameters(algorithm=algorithm, parameters_queue=parameters_queue, device=device)

좋은 가중치가 큐에 와 있어도 판이 끝나야 적용된다. 그래서 actor 를 재시작하면 최소 1판은 반드시 무작위 정책으로 돈다.

actor 가 처음부터 학습된 가중치를 쓰게 하는 법

--policy.path 로 체크포인트를 직접 지정하면 actor 가 기동할 때 가중치를 싣는다. 코드를 고칠 필요가 없다.

학습된 가중치로 actor 시작
bash scripts/train.sh actor --window \
  --policy.path=outputs/train/03_exp_b_assist/checkpoints/last/pretrained_model \
  --policy.online_steps=1000000

--policy.path 지정21 / 21 — 완전히 같다
online_steps 를 같이 줘야 한다

--policy.path 를 주면 policy 설정을 체크포인트의 config.json 에서 읽는다. 거기 적힌 online_steps 는 그 체크포인트를 만들 때의 값이다(예: 100,000). configs/*.json 을 나중에 고쳤다면 --policy.online_steps=<값> 으로 같이 덮어써야 actor 가 금방 끝나 버리지 않는다.

09b다 됐으면 — 모델 꺼내 두기

학습이 잘 끝났으면 그 가중치를 학습 폴더 밖으로 복사해 둔다. 체크포인트는 2,000 스텝마다 쌓이고 자동으로 지워지지 않지만, bash scripts/train.sh restart 는 outputs/train/<이름> 을 통째로 지운다. 같은 이름으로 다시 시작하는 순간 다 사라진다.

stop 은 보관이 아니다

bash scripts/train.sh stop 이 하는 일은 STOP_NOW 파일을 만드는 것뿐이다. learner 가 그걸 보고 체크포인트를 하나 남기고 종료한다 — 저장 위치는 여전히 outputs/train/<이름>/checkpoints/<스텝>/ 이다. 학습 폴더 밖으로 나가는 것은 아무것도 없다. 아래 복사는 사람이 직접 해야 한다.

체크포인트 한 개는 무엇으로 되어 있나

checkpoints/<스텝>/ 안에 세 폴더가 있다. 추론만 할 거면 첫 줄 하나면 된다.

폴더크기들어 있는 것언제 필요한가
pretrained_model/ 23 MB 정책 가중치 model.safetensors · 정규화 전처리기/후처리기 · config.json · train_config.json 추론·평가에 필요한 전부
algorithm/ 45 MB SAC 크리틱 · 그리퍼(이산) 크리틱 · 온도 학습을 이어 갈 때만

def sha(p):
    h = hashlib.sha256()
    with open(p, "rb") as f:
        for b in iter(lambda: f.read(1 << 20), b""):
            h.update(b)

끝낼 때는 Ctrl+C 말고 stop

learner 를 Ctrl+C 로 끄면 마지막 저장 이후 진행분이 사라진다. 체크포인트는 2,000 스텝마다 남으므로 최대 2,000 스텝을 잃는다. bash scripts/train.sh stop 을 먼저 치면 그 시점 체크포인트를 남기고 스스로 끝낸다. 그다음 actor 칸에서 Ctrl+C 로 정리한다.

끄는 방법체크포인트깨질 위험
train.sh stop그 시점으로 저장하고 끝낸다없음. 단 저장이 버퍼가 꽉 차 있으면 5~11분 걸린다 — 끝날 때까지 기다린다
learner Ctrl+C 한 번저장하지 않는다 — 마지막 정기 체크포인트로 돌아간다없음. 마침 저장 중이었으면 코드상 그 저장을 끝까지 마치고 꺼진다 — 5~11분 멈춘 것처럼 보인다. 이때 한 번 더 누르지 않는다
Ctrl+C 두 번즉시 강제 종료저장 중이었으면 버퍼 스냅샷(dataset/ · dataset_offline/)이 반쯤 쓰인 채 남아 다음 재개가 깨진다
서버 재시작 · pod 멈춤 · kill -9즉시 죽는다저장 중이었으면 위와 같다. 버퍼가 꽉 찬 뒤에는 시간의 약 61% 가 저장 중이다(03 Q16)
actor Ctrl+Cactor 는 저장할 것이 없다없음. 진행 중이던 한 판이 learner 에 안 갈 수 있을 뿐

근거: learner 는 첫 신호에 "끝내라" 표시만 하고 지금 하던 일(저장 포함)을 마친 뒤 루프를 빠져나온다. 두 번째 신호에 바로 종료한다(utils/process.py:85-99). 저장은 기존 스냅샷 폴더를 먼저 지우고 새로 쓴다(learner.py:685-702). 가중치 체크포인트와 checkpoints/last 는 그보다 먼저 써지므로 남는다 — 깨지는 것은 버퍼 스냅샷이다. 저장 도중에 Ctrl+C 를 누르는 경우는 코드로만 확인했고 실제로 시험하지는 않았다.
