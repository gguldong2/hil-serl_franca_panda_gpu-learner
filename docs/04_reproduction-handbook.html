RunPod 과 Docker — 결정: 우리 이미지는 만들지 않는다 (D1 = A)

RunPod 은 pod 를 만들 때 템플릿의 "Container Image" 칸에 적힌 이미지를 받아 와 그걸로 컨테이너를 띄운다. 공식 템플릿도 이 칸에 RunPod 이 만든 이미지 이름이 들어 있을 뿐이다. 그 칸에 우리 이미지 이름을 넣으면 우리 이미지로 뜬다.

  2. 빌드 · 업로드 — Docker 가 되는 PC 나 GitHub Actions 에서 docker build --platform linux/amd64 → docker push (Docker Hub 나 GHCR).
  3. 템플릿 — RunPod 화면에서 새 템플릿: Container Image 에 우리 이미지 이름, 볼륨은 /workspace, TCP 22 노출, 환경변수 NVIDIA_DRIVER_CAPABILITIES=all. 이미지가 비공개면 레지스트리 계정 정보를 RunPod 에 등록한다.

pod 안에서 docker run 을 하지 않는다 — 할 수도 없다

"Docker 로 한다" 는 것은 pod 가 만들어질 때 쓸 디스크 이미지를 우리가 준비한다는 뜻뿐이다. Docker 로 따로 띄우는 서버나 시스템은 없다. learner · actor · 대시보드는 지금처럼 SSH 셸에서 bash scripts/… 로 띄우는 보통 프로세스다. RunPod 은 GPU pod 안에서 Docker 를 또 돌리는 것(Docker-in-Docker)을 지원하지 않는다 — 공식 문서: "RunPod 이 Docker 를 대신 돌리므로 pod 안에서 자기 Docker 나 Compose 를 띄울 수 없다", Docker-in-Docker 튜토리얼은 CPU pod 용뿐이다(11-15 확인). 막힌 것은 "pod 안에서 컨테이너를 또 띄우기" 이지, "우리 이미지를 pod 로 띄우기"(B)가 아니다. 우리가 B 를 안 하는 것은 불가능해서가 아니라 D1 = A 로 정했기 때문이다.

반드시 지킬 것 — 오프라인 칸 ≥ 시연 프레임 수

시연은 시작할 때 오프라인 버퍼에 통째로 싣는다. 칸이 모자라면 learner 가 시작하자마자 ValueError 로 죽는다(buffer.py:443). Panda 시연 43판 = 19,612 프레임, UR5e 시연 29판 = 7,253 프레임. 그래서 메모리를 줄일 때는 온라인부터 줄인다.

오프라인 칸 − 시연 = 시연이 밀리기 전까지 받을 수 있는 개입

개입한 스텝은 오프라인 버퍼에도 들어가고, 꽉 차면 가장 오래된 것(원래 시연)부터 덮는다. Panda 시연에 오프라인 20,000 이면 남는 칸이 388 뿐이라 개입 두 판 만에 시연이 밀리기 시작한다. UR5e 시연(29판 7,253)이면 같은 20,000 에서 12,747 이 남는다. 24 GB 급에서 10,000 / 20,000 을 쓰면 이렇게 된다. 계산표는 03 문서 Q14.

왜 프로젝트 전용 venv 인가 — 템플릿의 PyTorch 는 언제 빌려 쓰나

02 는 프로젝트 폴더 안에 .venv(Python 3.12 + torch 2.11.0 등, 7.5 GB)를 만든다. 지금 서버도 같다 — 시스템 Python 은 3.10 이고 torch 가 없다. 모든 scripts/*.sh 가 scripts/env.sh 를 불러 이 venv 를 켜므로 평소에는 보이지 않는다(11-16 확인).

이유내용
버전을 고정해야 한다lerobot 0.6.1 은 Python ≥ 3.12, torch ≥ 2.7 · < 2.12 를 요구한다. RunPod PyTorch 이미지는 torch 2.6 · 2.7.1 · 2.8 · 2.9 · 2.12 · 2.13 이고 우리가 검증한 2.11 은 없다(Docker Hub runpod/pytorch 태그, 11-16 확인). 2.12 이상은 lerobot 이 받지 않는다. 2.9.1 은 11-19 L40S pod 에서 03_verify · 스모크(torch.compile 끔 · 켬)를 2.11 과 나란히 통과했다 — 긴 학습의 성공률 곡선은 아직 비교하지 않았다. 2.8 이하는 확인하지 않은 버전이다
멈춰도 남아야 한다 (RunPod)템플릿의 시스템 Python 에 lerobot 등을 깔면 컨테이너 디스크에 들어가 pod 를 멈출 때마다 지워진다 — 매번 02 수준의 재설치. venv 는 /workspace 안이라 남는다
섞이지 않아야 한다venv 는 기본으로 시스템 패키지를 보지 않는다. 템플릿의 torch · Jupyter 와 서로 건드리지 않는다. 실제로 이 서버에서는 ROS Jazzy 가 PYTHONPATH 로 끼어들어 env.sh 가 그것을 지운다. 템플릿 torch 를 빌려 쓰는 venv 만 예외로 시스템 패키지가 보인다 — venv 에 깐 것이 앞서므로 numpy 등은 venv 판이 쓰이고, 02 가 torch · torchvision · torchcodec 짝을 제약 파일(.venv/torch-constraints.txt)로 고정하며, pip check 는 프로젝트가 쓰는 패키지의 충돌만 막는다
아끼는 시간은 디스크에 달렸다로컬 디스크 서버에서는 torch 내려받기(약 3 GB, 몇 분)뿐이다. RunPod 은 다르다 — /workspace 가 네트워크 디스크(MooseFS)라 venv 의 torch 는 설치에 약 10분, 프로세스가 뜰 때마다 import 에 108초가 든다. 템플릿 torch 는 이미지 안(로컬 디스크)이라 4초다(11-19 L40S 실측). lerobot · gym-hil · 패치 · 나머지 의존성은 어느 쪽이든 venv 에 깐다

남는 충돌 경로는 환경변수뿐이다(PYTHONPATH · LD_LIBRARY_PATH). env.sh 가 앞의 것을 지우고, torch 는 자기 CUDA 라이브러리를 들고 오며, 02 가 설치 끝에 실제 GPU 계산을 돌려 보고 안 되면 멈춘다. 템플릿 torch 빌려 쓰기(11-19) — 02 는 인자 없이 돌 때 시스템 python3.12 의 torch · torchvision 이 검증한 조합(REUSE_STACKS: 2.11.0 · 0.26.0, 2.9.1 · 0.24.1)이고 GPU 계산이 되면 venv 를 --system-site-packages 로 만들어 그 torch 를 쓴다. 아니면 위처럼 venv 에 2.11.0 을 깐다. 빌려 쓴 venv 에는 .venv/hil-template-torch 가 남고, pod 를 다른 PyTorch 버전 템플릿으로 만들면 preflight 가 "템플릿 torch 가 바뀜" 으로 막는다 — --fix 는 02 를 돌려 venv 에 torch 2.11.0 을 따로 깐다.
